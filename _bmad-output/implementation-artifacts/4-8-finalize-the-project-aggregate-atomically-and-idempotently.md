# Story 4.8: Finalize the Project Aggregate Atomically and Idempotently

Status: in-progress

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Master Administrator,
I want the API to finalize the complete Project command atomically and idempotently,
so that either one valid `PLANNED` Project and all selected relationships are created or nothing is committed.

## Acceptance Criteria

1. **Given** the aggregate command reaches the API
   **When** request validation runs
   **Then** the body may not exceed 1 MiB
   **And** it permits at most 200 Employee allocations, 100 Machine allocations, 20 Technical Responsibilities, 10 Fuel Agreements, and 10 Break Templates.

2. **Given** the encoded request body is exactly 1 MiB and every collection is exactly at its documented maximum
   **When** request validation runs
   **Then** the request is accepted for domain validation
   **And** rejection occurs only when the body or a collection is greater than its inclusive limit.

3. **Given** the request exceeds any body or collection limit
   **When** it is validated
   **Then** the command is rejected before domain mutation
   **And** a stable validation code identifies the relevant limit.

4. **Given** a finalization command is accepted
   **When** the Projects service executes
   **Then** trusted Corporation, selected Company, User, Session, and role come from request context
   **And** all Project identity, baseline, Client, responsibility, schedule, break, Employee, Machine, and fuel data is revalidated inside one transaction.

5. **Given** all required and selected relationships remain valid
   **When** the transaction commits
   **Then** exactly one `PLANNED` Project, initial Project Baseline, current Client period, one Manager tenure, Technical Responsibilities, Weekly Schedule revision, Break Templates, optional allocations, optional Fuel Agreements, and initial effective prices are persisted
   **And** no actual production start is recorded.

6. **Given** optional mobilization collections are empty
   **When** finalization commits
   **Then** the Project is still created successfully
   **And** Client, Manager, at least one Technical Responsibility, and valid Weekly Schedule remain mandatory.

7. **Given** any validation, ownership, availability, uniqueness, temporal, or persistence rule fails
   **When** finalization executes
   **Then** the complete transaction rolls back
   **And** no Project, idempotency completion, allocation, responsibility, schedule, or agreement is partially committed.

8. **Given** the same scoped `Idempotency-Key` and canonical payload are submitted after a successful commit
   **When** the retry is processed
   **Then** the original successful result is returned
   **And** no duplicate Project or relationship is created.

9. **Given** the same scoped `Idempotency-Key` is submitted with a different canonical payload
   **When** the request is processed
   **Then** a `409` idempotency conflict is returned
   **And** the original result and aggregate remain unchanged.

10. **Given** concurrent identical finalization requests use the same key and payload
    **When** they execute
    **Then** one transaction creates the aggregate
    **And** the other request safely waits for or recovers the committed result.

11. **Given** finalization or an eligibility conflict completes
    **When** the API returns its canonical response
    **Then** success or authorized affected resource identifiers are represented through stable response codes and `details.resources`
    **And** completed idempotency records remain retained for 30 days.

12. **Given** aggregate finalization is tested
    **When** unit, real-PostgreSQL transaction and concurrency, and OpenAPI suites run
    **Then** they cover successful full and minimal aggregates, every request limit, complete rollback, eligibility races, same-key replay, key-payload mismatch, concurrent submission, and cross-scope rejection
    **And** every successful scenario commits exactly one Project aggregate.

## Dev Notes

### Developer Context

- Story 4.8 is the first persisted Projects vertical slice. Stories 4.1-4.7 intentionally define browser-local state and strict command fragments without creating partial backend records.
- The baseline contains no Projects module, Project tables, allocation tables, Fuel Agreement tables, or idempotency helper. This story must build the full aggregate rather than claim integration with nonexistent persistence.
- Existing Workforce/Fleet availability and Commercial blocker seams currently return placeholder no-allocation/no-agreement outcomes. Finalization must replace those seams with real current-state queries.
- Story 4.9 owns dashboard submission/recovery; this story owns the authoritative API, generated contract, transaction, and persistence guarantees.

### Public API Contract

- Endpoint: `POST /api/v1/projects` with trusted authenticated Company context and required `Idempotency-Key: <uuid-v4>`.
- Body composes the exact predecessor fragments: root identity/baseline fields; `clientId`; `managerEmploymentId`; `technicalResponsibilityEmploymentIds`; `weeklySchedule`; `breakTemplates`; `initialEmployeeAllocations`; `initialMachineAllocations`; `projectFuelAgreements`.
- Scope/audit/lifecycle fields are forbidden in the body. The server writes `PLANNED`, one transaction timestamp, trusted actor/session, and null actual production start.
- Success data is `{ projectId, status: "planned" }`. Completed identical replay returns the same resource and result.
- `PROJECT_WIZARD_BODY_TOO_LARGE`, `PROJECT_WIZARD_COLLECTION_LIMIT_EXCEEDED`, missing/invalid idempotency key, `IDEMPOTENCY_PAYLOAD_CONFLICT`, semantic validation, and scoped resource conflicts must be machine-readable.

### Persistence and Constraint Guardrails

- Temporal history uses half-open periods with one `effectiveTo = null` current row; closed history is immutable and never reopened.
- Add composite ownership foreign keys wherever practical. Partial unique indexes/check constraints must cover open Manager, responsibility/allocation/agreement/price periods and exact scope.
- Person exclusivity is Corporation-wide even when different Employments exist in sibling Companies. Machine exclusivity is per Corporation Machine and requires current Company ownership.
- Schedule days remain wall-clock defaults, not instants. Baseline dates remain civil dates. Decimal fields remain exact database numerics and API strings.
- Initial Machine allocation references the submitted-and-revalidated latest confirmed reading and creates a reading reference without changing the reading.

### Idempotency and Transaction Guardrails

- The idempotency uniqueness scope is Session + Corporation + Company + operation + key. A key used in another Session/Company/operation is independent.
- Only completed records survive commit. Aggregate failure rolls back both domain data and the in-transaction key reservation.
- Retain completed rows for 30 days with an explicit `expiresAt`; expired matching keys may be safely reclaimed inside a later command.
- Use `SERIALIZABLE` and bounded `P2034` retries as documented by Prisma; keep the transaction free of network calls and long non-database work.
- Treat a unique-key loser as a replay candidate after the winner commits; do not return a spurious duplicate-key database error.

### Architecture Compliance

- Preserve backend flow and domain ownership. Only handlers/ports with a transaction context access Prisma; controllers and services do not import generated Prisma types for persistence.
- Fastify route schemas own validation/OpenAPI. `bodyLimit` counts bytes before JSON parsing and must remain exactly 1 MiB for this route.
- Use canonical envelopes, stable codes, trusted request context, non-disclosing scope behavior, and structured resource details.
- No cache, message queue, event bus, distributed lock, second database, RLS claim, or asynchronous finalization is introduced.
- Generated Prisma/OpenAPI/Kubb artifacts are script outputs, never manual edits.

### Library and Framework Requirements

- Use repository-pinned Node `22.22.3`, PostgreSQL 16, Fastify `^5.8.5`, Prisma/adapter `^7.8.0`, Zod `^4.4.3`, TypeScript, Vitest, and generated Kubb `4.38.1` artifacts.
- Use Node `createHash("sha256")` over canonical UTF-8 JSON; do not add an idempotency or hashing dependency.
- Use Prisma interactive `SERIALIZABLE` transactions and retry `P2034` only within a bounded helper; do not retry arbitrary domain errors.
- Fastify's route `bodyLimit` is byte-based and defaults to 1 MiB, but set it explicitly to make the contract reviewable.

## Security and Completeness Hardening Amendment

The following criteria are mandatory extensions of AC 1-12 and take precedence where an earlier note is less specific:

- **H1 — Workspace precondition and authentication:** `POST /api/v1/projects` requires `X-Expected-Company-Id` in addition to `Idempotency-Key`. The header is a precondition only, never authorization authority. Before and inside the transaction, compare it with the authenticated Session's current Corporation, Company, active state, and `MASTER_ADMIN` role. A mismatch fails before mutation with a stable non-disclosing workspace-changed error.
- **H2 — Content and abuse limits:** Accept only `application/json`; keep the exact 1,048,576-byte route limit and all inclusive collection maxima. Apply a 10-attempts-per-minute limit keyed by trusted Session and Company, without including payloads or idempotency keys in logs or rate-limit responses.
- **H3 — Versioned canonicalization:** Hash `project-finalization:v1\n` followed by canonical UTF-8 JSON. Reject unknown fields; NFC-normalize bounded text; lowercase UUIDs; preserve explicit `null`; serialize decimals/dates in their already normalized wire forms; order object keys lexicographically; sort semantically unordered id-keyed sets by their stable ids; preserve the user-defined Break Template order. Canonicalization has shared golden fixtures in API and dashboard tests.
- **H4 — Idempotency state machine:** A record represents only a completed command and is inserted in the same committing transaction as its Project. A failed transaction leaves no reservation. Same scope/key/hash returns the original `201` result; same scope/key/different hash returns `409 IDEMPOTENCY_PAYLOAD_CONFLICT`. Expired records may be removed/reused only after the original Session is no longer active; cleanup never races an active replay.
- **H5 — Closed error contract:** `details.fields` is an ordered array of `{ path, code }`. `details.resources` is an ordered discriminated array of `{ kind, id, section, reason }`, where `kind` and `reason` are closed OpenAPI enums covering identity, accountability, Employee allocation, Machine allocation, Supplier and Fuel Type conflicts. Foreign/absent ids return the same generic code with empty resource details.
- **H6 — Executable invariant matrix:** Every invariant is mapped to one named enforcement mechanism and test: composite tenant foreign keys; partial unique indexes for one open Manager, Corporation Person allocation, Machine allocation, Project/Supplier agreement and Agreement/Fuel Type price; ordinary checks for scalar ranges/states; and deferred constraint triggers for minimum child cardinalities that cannot be expressed by a row check. Do not claim that a PostgreSQL `CHECK` can inspect other rows.
- **H7 — Transaction policy:** Use at most three `SERIALIZABLE` attempts for Prisma `P2034`, `maxWait` 5 seconds and transaction timeout 15 seconds, with bounded jitter outside the transaction. Each retry rereads all authoritative resources and the authenticated Session/Company. No network or generated-client call runs inside the transaction.
- **H8 — Deterministic concurrency proof:** Real-PostgreSQL tests use barriers/latches, not timing sleeps, to cover duplicate identical requests, divergent payloads, Person/Machine exclusivity, Manager uniqueness, latest-reading changes, Supplier/Fuel Type changes, and Company switching. Assert one winner where applicable, stable loser errors, intact idempotent replay, and zero partial rows.

### Mandatory Invariant Enforcement Matrix

| Invariant | Enforcement | Required proof |
|---|---|---|
| Tenant ownership and references | Composite foreign keys including `corporationId` and, for Company-owned rows, `companyId` | Cross-tenant insert/update fixtures fail without disclosure |
| One current Manager per Project | Partial unique index over open Manager tenure | Concurrent Manager inserts yield one current row |
| One open allocation per Corporation Person | Partial unique index on Corporation Person for `effectiveTo IS NULL` | Different Employments of one Person race deterministically |
| One open allocation per Machine | Partial unique index on Machine for `effectiveTo IS NULL` | Concurrent Projects race deterministically |
| One current agreement per Project/Supplier | Partial unique index for open period | Duplicate/concurrent agreement fixtures fail atomically |
| One current price per Agreement/Fuel Type | Partial unique index for open period | Duplicate/concurrent price fixtures fail atomically |
| Required Manager, Technical Responsibilities, seven schedule days, and agreement fuel-type children | Deferred constraint triggers evaluated at transaction end | Missing-child fixtures roll back the aggregate |
| Scalar bounds, enums, date order and decimal capacity | DTO validation plus database `CHECK`/column capacity where independently expressible | Boundary and direct-database fixtures agree |

Implementation tasks must update the migration review checklist, OpenAPI/Kubb schemas, idempotency helper, error mapper, rate limiter, transaction helper, and cross-application golden fixtures to match H1-H8 exactly.
